## 1. The binding constraint (everything follows from it)
The scorer runs tasks **serially** (`swegemma.config.concurrency = 1`), 12 h wall for ~120 hidden tasks on 4×L4 (TP=4):
≈ 5.5 min/task. Decode at batch 1 is ~35 tok/s (87 % of task time) ⇒ **~10–11k generated tokens per task, total**.
Two consequences:
1. A token of thinking must buy more than it costs. C11t does (+0.165 for ~1.04–1.25× time) — ship it behind the gate.
2. Decode is memory-bandwidth-bound: 2–4 concurrent sequences cost ~1.1–1.4× the wall time of one. The only way to use
   that slack under serial scoring is **intra-task parallelism**, and the submission schema allows it
   (`adk_submission.schema`: SandboxedParallelAgentConfig / Sequential / Loop). This is the unexploited lever.

## 3. L2 design sketch (needs the feasibility spike first)
root = SequentialAgent[ ParallelAgent[solver_a, solver_b, (solver_c)] → selector ]
- Each solver works in its own copy (`git worktree add /tmp/ws_<name>` or `cp -a`), writes `/tmp/patch_<name>.diff`
  (+ its failing-first repro test `/tmp/repro_<name>.py`). Different strategies: (a) repro-first, (b) test-first
  (find nearest existing test, make it fail), (c) analyzer-plan-first.
- Selector: for each candidate diff → `git apply --check`, apply to /workspace, run all repro tests + nearest existing
  tests (`pytest -x -q`, 60 s cap), score = (#repro pass, #existing pass, −patch size); keep best; revert others;
  fall back to the first syntactically valid patch; never submit an empty patch if any candidate applies.
- Checked 12:25: `swegemma/context.py` keeps ONE `tool_calls_used` counter per task run (incremented at every tool
  call, line 549) ⇒ sub-agent calls share the 100-call budget ⇒ K=2 with ~40 calls each + ~10 for the selector;
  (1) prompt-level per-solver caps are mandatory; (2) can `edit_file`/`read_file` touch /tmp (write_file cannot)? If not, solvers use the
  python-heredoc edit route; (3) wall time on L4 (prefill contention) — Kaggle timing kernel on 30 ids.
- Published analogues: Agentless (repro-test selection), CodeMonkeys (test voting), R2E-Gym hybrid verifiers,
  SWE-Gym verifier best-of-N — all report +8…+15 pts absolute at N=4–8 for 32B-class models; expect ⅓–½ of that at K=2–3.

### 6b. Test-time scaling + scaffold design (research agent, 12:40)
Selection methods ranked by gain per extra wall-clock when N parallel samples cost ~1.2–1.5× one:
1. **Parallel N + execution filters**: regression tests first, then model-generated repro tests (Agentless Lite 25.7→32.0, the
   repro-test filter alone +5; Trae-Agent N=3: +5…+9 pts with dedup → regression tests (recall 93 %, precision 61 %) → AST-equivalence
   vote → LLM review; R2E-Gym hybrid Best@16 34.4→49.4). **5 extra test-writer rollouts beat 5 extra edit rollouts** (R2E-Gym);
   >80 % of tasks have <20 % discriminative tests and ~10 % have "toxic" tests → never trust a single generated test.
2. Execution-free scoring (LLM judge / trained verifier) only to rank test-passing survivors (+6…+8 over either alone); judges
   without trajectory context are style-biased.
3. Normalized-diff / AST majority vote as a free tiebreak (degrades at large N). AggAgent (2026): an aggregator agent that reads the
   parallel trajectories via tools, +5.3 abs, overhead ≤ 1 rollout — this is our ParallelAgent → selector shape.
4. Sequential search (MCTS / PRM beam / SWE-Replay / EGSS) gives real gains but serial latency — not for our regime.
Scaffold/ACI evidence: SWE-agent ACI +10.7 pp over bare shell (100-line viewer, lint-on-edit, search returns file names only);
mini-SWE-agent: bash-only + linear history works for any LM; **observations are ~84 % of a turn** — masking old observations
halves cost at ≈ equal accuracy, and for weak models *pruning beats LLM summaries* (summaries lengthen trajectories +15 %);
successful trajectories are < 20–30k tokens; a length-10 repeated action sequence = 89 % failure (SWE-smith); guarding mutating
steps +7 % (SABER); Qwen3-32B tool-error rate 42 % → lint-on-edit, compact outputs.

**Refined L2 design (replaces §3's sketch):** root = Sequential[ Parallel[solver_A (repro-first), solver_B (test-first),
test_writer (writes 2–3 discriminative tests for the issue, verifies they FAIL on the base)] → selector ].
Shared 100-call budget split by prompt caps: solvers 35 each, test_writer 15, selector 15. Selector order: (1) `git apply --check`
+ `py_compile`; (2) nearest existing tests (regression, high recall); (3) the generated tests (discriminative, never a single one);
(4) normalized-diff agreement; (5) smaller patch. Never submit empty if any candidate applies. Time target ≤ 1.4× C11t on L4.
Also: add a root-level anti-repetition rule + "trim observations" discipline (head/grep only) to every candidate (L6/L8).
