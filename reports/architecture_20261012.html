How Gemma_RL runs

We compete in Kaggle's Gemma 4 Developer Agent challenge. The model is fixed: Gemma-4-31B, int4. What we submit is an agent configuration: YAML, prompts and small skill scripts that tell the model how to fix a bug in a repository. Kaggle runs it on about 120 hidden tasks and scores how many fixes pass the tests. Everything in this repo exists to find a better configuration and hand you one zip a day.

1 · The autopilot loop

There are three places where code runs. You and Kaggle are at the top. In the middle is the cluster's login node: CPU only, but it has internet, and the Claude "brain" runs there. At the bottom are GPU nodes rented through SLURM, which do the heavy evaluation. Nothing in the loop needs you except the upload.

  1. Watchdog and daemon. A cron job on login2 restarts ops/autopilot/daemon.sh whenever it is not running. The daemon starts a headless claude -p cycle every 2 hours (Sonnet, 30-minute hard cap). The first cycle after 09:00 each day is a release cycle. All others are work cycles.
  2. The Claude cycle reads its brief and memory. Its prompt is CHARTER.md (mission, hard rules, compute limits) plus prompts/work.md or prompts/release.md. It reads STATE.md first and updates it last. Nothing else carries over between cycles.
  3. Build a candidate. Each idea becomes a new folder submissions/cXX_… that changes one thing compared with the current base. scripts/package_submission.sh validates it with the organizers' compiler.
  4. Queue it. ops/queue/enqueue.sh writes one small text file per shard × seed into ops/queue/pending/. The queue is just files that move between pending/, running/, done/ and failed/.
  5. GPUs pick it up. Every 10 minutes, ops/slurm/gpu_filler.sh submits ap_worker jobs onto GPUs that are free right now. It holds at most 16 GPUs so teammates keep their headroom. Each GPU starts its own vLLM server, claims items by an atomic mv, and runs src/eval/run_eval.py, our copy of the Kaggle scorer.
  6. Report and decide. ops/queue/px_report.py compares the candidate with the base on the same tasks and seeds. src/analysis/time_budget.py estimates the time on Kaggle's L4 GPUs. The cycle writes the verdict to STATE.md and reports/council/DECISIONS.md, then commits.
  7. Release. If a candidate passes both gates, the release cycle builds submissions/daily/<date>/submission_….zip. Line 1 of RELEASE.md says which zip to upload. You upload it and log the score with ops/autopilot/ctl.sh lb <zip> <score>.

2 · What a submission actually is

A submission is a declarative Google ADK agent. Kaggle loads agent.yaml, gives the agent a bug report and a sandboxed repository, and keeps the patch the agent submits. We cannot add Python callbacks or custom tools. The levers we do have are prompts, sampling and thinking settings, how sub-agents are wired, and "skills": small stdlib scripts the agent can run inside the sandbox. This figure compares what ships today with what is being tested.

The edit-engine skill exists because of a bug we found in the model's chat template. It sorts tool arguments alphabetically, so in edit_file the model writes new_string before old_string. When it closes the long string badly, the following arguments get swallowed. In C9e that made 78–84% of edit calls fail. C23 drops edit_file and sends edits through run_command, which takes a single argument, into /tmp/ae.py. Malformed edits went to zero and time per task fell 22%.

3 · How a change becomes a release

Every idea goes through the same two gates. The accuracy gate uses our offline proxy benchmark: 152 mined tasks from 16 repos not in the public set. It is split into 8 shards and run with at least 2 seeds, because run-to-run noise is about ±0.03. The runtime gate exists because a submission that runs past 12 hours on Kaggle scores nothing; C4 and C9e both timed out.

Why not just tune on the public tasks? The early C-series did exactly that and it didn't carry over. The hidden set covers about 13 repos, roughly 9 of them private. That is why the proxy is built from unseen repos and every comparison is paired.

5 · Steering it

Controls

Run these from login2, which is where the daemon lives. This session is on login1, which has no autopilot cron.

  • ops/autopilot/ctl.sh status: daemon, recent cycles, SLURM jobs
  • ctl.sh pause / resume: do this before working by hand
  • ctl.sh lb <zip> <score>: record a leaderboard result
  • ctl.sh tail: watch the current cycle's tool calls
  • touch ops/slurm/FILLER_STOP: stop new GPU jobs

Files to read first

  • ops/autopilot/STATE.md: current status and next step
  • ops/autopilot/CHARTER.md: mission and hard rules
  • reports/council/DECISIONS.md: why things were chosen
  • submissions/daily/LATEST/RELEASE.md: what to upload today
  • reports/scoreboard.md: all candidates side by side

Supporting pipelines

  • src/mining → data/derived/proxy: builds the 152-task proxy benchmark
  • src/sft: LoRA fine-tuning and distillation (parked, no gain over C9e so far)
  • src/analysis: failure forensics, L4 time model, edit replay
  • scripts/kaggle_eval: private Kaggle 4×L4 timing kernels

Hard rules the autopilot follows

  • Never submits to Kaggle itself. You upload.
  • Holds at most 16 GPUs and only cancels jobs named ap-*.
  • Never edits a submission folder that already has an LB score.
  • Commits at the end of every cycle; no destructive git.
