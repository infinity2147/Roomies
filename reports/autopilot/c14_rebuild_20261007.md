## 1. What `max_time_minutes` does (harness evidence, `.venv-eval/lib/python3.13/site-packages/`)

Location in the submission: `eval_config.yaml` at the zip root, key `evaluation.max_time_minutes` (same schema C6a_t5 shipped,
`submissions/c6a_t5/eval_config.yaml`; D26 records that the scorer honoured it). Our proxy and Kaggle kernels read it the same way
(`src/eval/run_eval.py:33-43`, `scripts/kaggle_eval/kernel_template.py:215-237`; scorer defaults 300 s / 100 calls / 60 min).
Note: the organizers' Python package itself has no `eval_config` reader (grep over swegemma/adk_submission/adk_eval_core is empty);
the scorer notebook parses it and passes `max_time_minutes=` to `EvalConfig` (`swegemma/config.py:106,148-152` -> `budget.time_minutes`).

What happens at the cap (`swegemma/harness/agent_runner.py`):
- The whole agent loop runs under `asyncio.timeout(budget.time_minutes*60)` (`:433-443`, `:498`); the loop also breaks when
  `context.elapsed_seconds > timeout_sec` after each event/turn (`:581-586`, `:639-644`). `elapsed_seconds` is the *agent session*
  time, not setup/verification (`swegemma/context.py:452-456`).
- On `TimeoutError` the error string is `Agent exceeded session timeout (N min)` (`:741-745`), **but the patch is not discarded**:
  if `submit_patch` was never called, the harness runs `git add -N . && git diff --binary _swegemma_baseline` in /workspace and uses the
  working-tree diff as the patch (`:757-776`, "Captured unsubmitted working tree modifications as fallback patch"). The task scores 0 only
  if the tree is clean or the fallback diff fails to apply / fails the tests.
- Tools are clipped too: `run_command` timeouts are `min(command_timeout, remaining)` with a 5 s floor (`swegemma/tools/execution.py:31-47`);
  with no time left the sandbox returns "Execution time budget exceeded." (`adk_eval_core/sandbox/base.py:188-196`) and every tool returns
  `TimeoutExceeded` (`swegemma/context.py:530-545`).
- The agent is told the budget: the task prompt gets `- Time allowance: N minutes` (`agent_runner.py:70-74`) and `get_status` reports
  `time_seconds_remaining` / `max_time_minutes` (`execution.py:125-126`), so the prompt's "25% remaining" rule is cap-aware.

Consequence for the cap choice: a timeout keeps whatever edits are on disk at that moment (unverified; scratch files or unreverted test
edits in /workspace would also be included), so the relevant cost metric is "solves whose *last edit* happens after the cap", not
"solves that finish after the cap".

## 2. Timing of C11t's passing tasks (`results/px/px_c11t_s1/s*/traces`, agent `elapsed_s` of the last step; 152 tasks, 74 resolved)

A100 proxy numbers are **not** scorer numbers: the proxy runs many concurrent tasks against a shared vLLM server, so per-task agent
time is inflated. C9ae measured on both: A100 proxy mean 12.59 / median 8.23 min vs the serial L4 kernel mean 4.92 / median 3.08 min
(`capture_task_times.py c9ae-t30s`), i.e. **L4 serial ~ 0.39 x A100 proxy**. The "L4 is 1.5-2x slower" assumption in the task brief is
the wrong direction for these runs; the table shows A100 raw, the measured 0.39 scale and a conservative 0.5 scale.

(C9ae L4 spans, min: 2.0 6.6 9.4 6.6 9.7 17.3 5.1 5.0 2.3 5.7 1.9 3.1 14.3 5.0 1.4 11.0 1.0 2.6 12.1 3.5 3.0 2.2 3.0 0.8 0.9 1.6 2.1 2.3 4.5 1.2;
0.3 min/task = L4 wall 2.6 h minus agent time over 30 tasks; 0.5 h = kernel startup. C11t on L4 is predicted 1.04 x C9ae by the D25 model.)

**Recommendation: `max_time_minutes: 5`** (as built). Reasons: (a) it is the largest cap that still guarantees < 12 h at N = 120 even
if every task hits the cap (11.1 h); 6 min already needs the tail to behave (13.1 h worst case) and 8 min is no insurance at all;
(b) the cost difference between 5 and 6 is ~1 solve in 74 (56 vs 58 last-edit-before-cap at the measured scale), because C11t's
solves are bimodal (either < 4 min or > 8 min on L4-equivalent time); (c) expected cost of 5 min: roughly 24-32% of C11t's proxy solves
are cut (~6-8 of 25 tasks per 120 on a hidden set at C11t's proxy rate), of which most keep their diff via the fallback. This is an
insurance policy with a real premium: use it only when the L4 gate (D25, ratio <= 1.10) fails or a thinking variant is otherwise
untimeable, which is exactly how the strategy memo frames L7/L1.
Two caveats for testing c11tc on the proxy: (1) a 5-min cap on the A100 proxy corresponds to a ~2-min cap on L4, so a paired proxy run
of c11tc vs C11t would overstate the loss ~3x; to emulate the scorer on the proxy use `max_time_minutes: 13` (5 / 0.39), or judge it on the
L4 kernel only. (2) The cap counts agent session time only; the 0.3 min/task setup+verify and the ~0.5 h startup are outside it.
