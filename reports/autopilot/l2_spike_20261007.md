# L2 feasibility spike: intra-task best-of-K via ParallelAgent (2026-10-07, login node, ~40 min)

Scope: strategy memo §1–§3 (refined design §6b). Evidence paths are relative to
`.venv-eval/lib/python3.13/site-packages/` unless they start with `src/` or `submissions/`. No GPU work was done.
Prototype: `submissions/c14p_bestof2/` (validated + zipped to `results/c14p_bestof2_submission.zip`; NOT enqueued, NOT submitted).

## Verdict
Feasible, but not the symmetric design of memo §3. The schema and ADK runtime support
`Sequential[Parallel[a,b] -> selector]` without harness changes, the parallel solvers are context-isolated by ADK branches,
and the final patch is whatever the last agent leaves in /workspace (or explicitly submits). Two hard facts shape the design:
(1) the file tools (`read_file`/`edit_file`/`write_file`) cannot touch anything outside /workspace, so a solver in `/tmp/ws_x` is
shell-only; (2) all tools share one 100-call counter and ADK executes our sync tools inline on the event loop, so only LLM decode
overlaps across the two solvers; tool execution serialises. Hence the prototype is **asymmetric**: solver_a keeps the strong tools in
/workspace, solver_b works shell-only in a `cp -a` copy at /tmp/ws_b, and a mechanical selector tests both diffs.

## Q1. Path restrictions per tool
- `read_file`, `write_file`, `edit_file` all call `_resolve_workspace_path()` (swegemma/tools/workspace.py:22-56), which strips a
  `/workspace/` prefix and raises `Path traversal detected` for any other absolute path (workspace.py:43-50) or anything that resolves
  outside `/workspace` (workspace.py:47-50). Callers: read_file:113, write_file:190, edit_file:239. **None of the three can read or write /tmp.**
  (The C11t prompt's statement "write_file cannot write outside /workspace" is correct and extends to read/edit.)
- `run_command` (swegemma/tools/execution.py:20-72) passes the string straight to `docker.exec`; no path or cwd check. Docker exec runs
  `timeout -k 5s <t> /bin/bash -c <cmd>` (sandbox/docker.py:705-712) in the container's working dir `/workspace`
  (docker.py:90, `environment TEST_TMPDIR=/tmp` docker.py:93 → /tmp exists and is writable). Every call is a fresh shell: `cd` does not persist.
- So `git worktree add /tmp/ws_b` and `cp -a /workspace /tmp/ws_b` both work from the shell tool (git is present: the harness itself
  runs `git add -A && git commit … && git tag -f _swegemma_baseline`, harness/container_setup.py:581). Our offline runner uses the
  subprocess sandbox, which regex-translates `/tmp` and `/workspace` inside commands to per-sandbox dirs (sandbox/subprocess.py:436-447),
  so the same commands work offline (`PYTHONPATH=/tmp/ws_b:…` translates because the match is only guarded by `[\w.-]`).
- Caveat for copies/worktrees: the package is installed pointing at /workspace, so a solver must run with
  `PYTHONPATH=/tmp/ws_b:/tmp/ws_b/src` (PYTHONPATH precedes `.pth`/editable finders). In-place compiled extensions are copied by
  `cp -a` but not by `git worktree`; the prototype uses `cp -a` + `git reset --hard _swegemma_baseline && git clean -fdq` (also undoes any
  edits solver_a already made in /workspace before the copy).
- Skill scripts are NOT free: `AdkSandboxCodeExecutor.execute_code` calls `budget_check_fn()` = `context.check_budget` with the default
  `count_tool_call=True` (adk_eval_core/sandbox/base.py:179-180; harness/agent_runner.py:327-332). They are written to the sandbox work dir
  and run as `python3 <file>` (base.py:202-208). This also applies to C13t's `repo-locate` (one counted call per invocation).

## Q2. Expressing Sequential[Parallel[a,b] -> selector] in agent.yaml
- `SandboxedSequentialAgentConfig` / `SandboxedParallelAgentConfig` (adk_submission/schema.py:326-348) accept only
  `name`, `description`, `agent_class`, `sub_agents: [ {config_path: …} ]` (+ `before/after_agent_callbacks`, ignored by swegemma).
  No model, instruction, tools or generation config at the workflow level; `extra="forbid"` (schema.py:247).
  `config_path` is relative to the referencing file (builders/sub_agents.py:56-67 sets `ctx.current_dir`).
- Each LlmAgent sub-agent is a full `SandboxedLlmAgentConfig` (schema.py:257-299): its own `instruction`, `tools` allowlist,
  `generate_content_config` (incl. `thinking_config`), `output_key`, `include_contents`. Compiled by builders/llm.py:62-88;
  `model` must be declared in each LlmAgent (no LlmAgent ancestor to inherit from) and `validate_single_declared_model` requires one name.
  Confirmed per-agent thinking: all three compiled agents carry `extra_body.chat_template_kwargs.enable_thinking=True`,
  `thinking_token_budget=4096` (checked by compiling the prototype).
- Tools: all names resolve against the one `SwegemmaContext.create_tools()` registry (tools/__init__.py:37-45), so sub-agents share the
  **same** tool instances and the single counter: `check_budget` increments `self.tool_calls_used` under a lock
  (swegemma/context.py:467-549, increment at :549). There is no per-agent `max_tool_calls`/turn/thinking budget (harness_knobs §Q1).
  ADK `RunConfig(max_llm_calls=remaining)` is set once on the root (agent_runner.py:516) and counts all LLM calls in the invocation.
- No transfer tools are injected: ADK adds parent/peer transfer targets only when the parent has `disallow_transfer_to_parent`
  (i.e. is an LlmAgent) (google/adk/flows/llm_flows/agent_transfer.py:156-175); a workflow parent does not.
- Instruction templating: ADK substitutes `{name}` with session state and **raises KeyError** for unknown names
  (google/adk/utils/instructions_utils.py:104-122); `{name?}` is optional. Prompts must avoid all other `{identifier}` text
  (e.g. `${p}` in shell). The prototype uses `{solver_a_report?}` / `{solver_b_report?}` filled by the solvers' `output_key`.

## Q3. Offline runner (src/eval/run_eval.py) with a workflow root
- `run_eval.py` only builds `EvalConfig` (sandbox="subprocess", compaction, context cache; src/eval/run_eval.py:70-100) and calls
  `swegemma.evaluate.Evaluator.run()`; the agent is compiled by the harness (`compile_submission`, agent_runner.py:334-345) which dispatches
  on `agent_class` (adk_submission/compiler.py:230-241). Nothing in run_eval/harness_patches/validate_submission assumes an LlmAgent root:
  the harness reads `getattr(agent, 'instruction', None)` defensively (agent_runner.py:446-457) and `describe()` walks `sub_agents`.
  `validate_submission` + `package_submission.sh` pass on the prototype (tree printed: Sequential > Parallel > solver_a/solver_b, selector).
- Differences that matter offline: (a) the subprocess sandbox path translation above; (b) our runner sets
  `EventsCompactionConfig(token_threshold=14336, …)` and the scorer's value is unknown (EvalConfig default None, swegemma/config.py:117),
  so **the selector must not depend on the transcript**: with `include_contents: default` it would receive both solvers' full histories
  rendered as `For context: [solver_x] called tool … returned result: …` user messages (contents.py:625-672; branch filter lets a
  branch-less agent see everything, contents.py:748-765). The prototype sets `include_contents: none` on the selector, whose "current turn"
  then starts at the last other-agent reply (contents.py:542-580) — it sees one solver's final message plus the two reports injected by templating.
- Trajectory/forensics scripts that key on a single root author (`agent.name` is passed to `handle_adk_event`, agent_runner.py:526)
  will see three authors; `context.handle_adk_event` itself ignores the author for counting (context.py:210-250). Check
  `src/analysis/forensics` parsers before using them on C14p runs (not done in this spike).

## Q4. How the run ends; concurrency; state
- End conditions in the root loop (agent_runner.py:504-690): (a) a text-only final event from any non-user author **while
  `context.patch_submitted` is true** breaks the stream (:566-579); (b) after `run_async` returns, `patch_submitted` → done (:635-637);
  else tool-budget / turn / timeout checks, else up to `max_nudges = 3` continuation messages (:499, :698-718).
  **Consequence 1**: solvers must NOT have `submit_patch` — a solver's submit + final text would break the stream mid-Parallel and skip the selector.
  **Consequence 2**: a nudge re-runs the ROOT: `_find_agent_to_run` only returns a non-root agent if every ancestor has
  `disallow_transfer_to_parent` (google/adk/runners.py:1119-1150); the selector's parent is a SequentialAgent → root → both solvers run again.
  The selector therefore must always `submit_patch`; the prototype budgets 12 calls for it and tells it so.
- Final patch: `submit_patch` stores `git diff --binary _swegemma_baseline` of /workspace (execution.py:86-99; repeatable, last wins). If nothing
  was submitted, the harness captures the unsubmitted /workspace diff as a fallback (agent_runner.py:758-776). So the patch is **always the
  /workspace tree** regardless of which agent ran last; /tmp content is irrelevant to scoring — this is why only the selector writes to /workspace at the end.
  Graceful degradation: if the budget dies before the selector, every selector tool returns BudgetExceeded and the fallback picks up
  whatever solver_a left in /workspace (≈ a capped C11n).
- Concurrency: ParallelAgent runs sub-agents as asyncio tasks in one TaskGroup (google/adk/agents/parallel_agent.py:51-87, :164-200) with
  branch contexts `parallel_solvers.solver_a` / `.solver_b` (:35-48) — same session, same /workspace, same container. Solvers do not see each
  other's events (branch rule contents.py:756-765) but they DO share the file system → isolation is mandatory and is the solver's own job
  (prototype: solver_b copies to /tmp/ws_b as its first call). swegemma tools are plain sync functions executed inline by ADK
  (google/adk/tools/function_tool.py:231-240; swegemma/tools/execution.py:135-148), so a 60 s pytest in one solver stalls the other's event
  processing (its vLLM stream keeps generating into the HTTP buffer). Expect decode overlap only.
- Session state is shared and not branch-scoped: `output_key` from each solver lands in `session.state` and is visible to the selector via `{key?}`.

## Prototype design (submissions/c14p_bestof2)
```
agent.yaml                  SequentialAgent bestof2_root
  sub_agents/parallel_solvers.yaml   ParallelAgent
    sub_agents/solver_a.yaml  LlmAgent, tools run_command/read_file/edit_file/write_file/get_status, output_key solver_a_report
    sub_agents/solver_b.yaml  LlmAgent, tools run_command/get_status, output_key solver_b_report
  sub_agents/selector.yaml   LlmAgent, tools run_command/get_status/submit_patch, include_contents: none
configs/sampling.yaml        = C11t (T 0.2, 8192 out, thinking 4096, include_thoughts true) for all three agents
```
- solver_a (prompts/solver_a.md): C11t workflow minus analyzer (C11n evidence) and minus submit; repro-first; cap 40 calls (wrap-up at 32);
  repro at /tmp/repro_a.py must fail-before; saves `/tmp/patch_a.diff` and leaves edits in /workspace; ends with a 4-line report.
- solver_b (prompts/solver_b.md): first call `cp -a /workspace /tmp/ws_b && git reset --hard _swegemma_baseline && git clean -fdq`; every
  command prefixed `cd /tmp/ws_b && export PYTHONPATH=…`; test-first (nearest existing test → new failing test in /tmp/test_b.py, fallback
  /tmp/repro_b.py); heredoc edits only; cap 35 calls (wrap-up at 28); saves `/tmp/patch_b.diff`.
- selector (prompts/selector.md): 5 fixed shell steps: (1) snapshot /workspace → patch_a (freshest), hard-reset, `git apply --check` both;
  (2) one-shot scoreboard: for each candidate apply → py_compile changed files → run repro_a, repro_b, test_b (each `timeout 60`) → reset;
  (3) nearest existing tests from the reports (`timeout 60 pytest … | tail -3`) per candidate; (4) rank: repro/test passes > fewer
  existing-test failures > smaller diff, ties → a; `--3way` fallback; (5) apply winner, `rm -rf /tmp/ws_b`, `submit_patch`, one-line answer.
  Never submits an empty tree if any candidate applies. Cap 12 calls. Budget plan 40+35+12 = 87 of 100 (13 slack).
- Why asymmetric instead of memo §3's two worktrees: file tools can't reach /tmp (Q1), and the edit-fallback result (C9ae) shows `edit_file`
  matters; keeping solver_a in /workspace preserves a near-C11n baseline inside the pipeline, so the worst case is "capped C11n", not "two
  heredoc-only solvers". A later variant can move solver_a too if solver_b's heredoc route proves as good.
- Validation: `scripts/package_submission.sh submissions/c14p_bestof2` → OK, zip written; compiled tree and thinking flags checked.

## Known risks (ranked)
1. **Shared budget overrun**: solvers ignore prompt caps (Gemma miscounts) → selector starts with few/no calls → fallback = solver_a's
   tree unselected. Mitigation in prompt (wrap-up thresholds, `get_status`); measure `tool_calls_used` at selector start from logs.
2. **Wall time**: two decode streams (~1.1-1.4x) + serialised tool execution + selector's 3-5 extra pytest runs (≤60 s each) + `cp -a`.
   Expect 1.3-1.7x C11t per task on L4; must be gated by the Kaggle timing kernel (12 h / 120 tasks).
3. **solver_b correctness**: forgetting the `cd /tmp/ws_b && PYTHONPATH` prefix silently tests /workspace (solver_a's tree); heredoc edits
   have a higher error rate than `edit_file`; compiled extensions or non-editable installs may not import from the copy; /tmp disk for `cp -a`.
4. **Nudge re-entry**: if the selector ends without `submit_patch` and budget remains, the whole Sequential re-runs on a mutated /workspace.
5. **Selector context**: with `include_contents: none` it relies on the two reports; if a solver's final text is not a report (budget death),
   the selector still works from the files alone (step 1 inventory). Transcript-free selection also means no AggAgent-style reading of trajectories.
6. **Templating KeyError**: any `{identifier}` added later to a prompt (e.g. `${var}`, a Python dict literal) crashes the agent at the first LLM call.
7. Forensics/trajectory tooling may assume one author; proxy results parsing should be unaffected (resolved/not per task).

## Recommended test plan
- Stage 0 (smoke, 1 GPU job, concurrency 2): shard `ops/queue/shards/proxy/s0.txt` (19 tasks) with C14p; check from logs: selector reached
  on ≥ 90 % of tasks, tool calls at selector start ≤ 90, no KeyError/compile errors, no empty patch when a candidate applied, per-task wall
  time vs the C11t s1 run on the same shard.
- Stage 1 (paired): shards s0-s3 (76 tasks), seed 1, paired vs C11t seed 1 (same shards, already run) → sign-z; promote to s4-s7 + seed 2
  only if the paired delta ≥ +0.03 and the wall-time ratio ≤ 1.6. Target n ≥ 150 x 2 seeds before any release decision (memo §4 rules).
- Timing gate: Kaggle 4xL4 serial kernel on the 30-id timing set vs C9ae; L2 is only shippable if (ratio vs C9ae) x 5.5 min ≤ ~7.5 min/task
  (i.e. ≤ 1.35x C9ae) or paired with an `eval_config max_time_minutes` cap (L7).
- Ablations worth queuing after stage 1: (i) solver_b with the analyzer-free C11n prompt in a second /workspace copy made by `git worktree`;
  (ii) K=3 with a test_writer (memo §6b) — only if stage 1 shows tool-budget headroom (≥ 15 calls unused on median).
